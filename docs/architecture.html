The one architectural idea to remember Retrieval is hybrid, not pure vector search. Small, categorical data (7 managers, ~9 projects, 12 technologies, 97 names) means "list everyone on MPLS" is an exact filter, while "who keeps the network reliable?" is a semantic match. The retriever picks per question.

Trade-offs to say out loud (the part that scores)

Traffic / scaling: sync request→response vs. async queue + workers. Pick: async for the LLM hop. The model call is slow (hundreds of ms–seconds), so a synchronous tier ties up a thread per request and collapses under a spike. A queue + worker pool decouples arrival rate from processing rate and lets each scale independently — cost is an added latency floor and more moving parts, so keep a fast sync path for cache hits.
Statelessness: in-process memory (today) vs. Redis-backed sessions. Pick: externalize state. The moment there's more than one replica, in-RAM history (Phase 8b) breaks — turn 2 may hit a different pod that never saw turn 1. Session state in Redis makes every replica interchangeable, which is what lets the app tier autoscale at all.
Authorization in RAG — the subtle trap: filter-before-retrieve vs. filter-after. Pick: apply the user's ACL as metadata filters INSIDE retrieval. If you retrieve freely and filter the final text, forbidden records still entered the LLM's context and can leak through the answer. Enforce the ACL as a where filter at the vector query (and at _execute_plan's store.get) so the model never sees what the user can't.
Tenant isolation: shared index + metadata ACLs vs. index-per-tenant. Pick: depends on blast-radius tolerance. Shared index is cheap and simple but one ACL bug leaks across tenants; per-tenant indexes give hard isolation at higher ops/cost. Start shared with strict filters; graduate sensitive tenants to dedicated indexes.
LLM as the bottleneck: call the model every time vs. cache + degrade. Pick: semantic cache + timeouts + graceful degradation. Coalesce identical in-flight questions, cache hot answers/embeddings, cap concurrency, and on timeout fall back to retrieval-only ("here are the matching records") rather than failing. Trade: cache staleness vs. cost & latency — bound it with a short TTL and invalidate on reindex.
Vector store: embedded Chroma (today) vs. managed/distributed (pgvector / Pinecone / Milvus). Pick: managed once it's multi-replica. Embedded is perfect for a single-node prototype but can't be shared across pods or scaled/replicated. Managed adds cost and a network hop but gives durability, concurrency, and horizontal scale.
Freshness vs. availability: live-mutate the index vs. blue/green reindex. Pick: versioned index + atomic swap. HR data changes rarely, so rebuild a new index offline and swap pointers — readers never see a half-updated index. Trade: a bounded staleness window between HR change and swap, which is fine for this domain.

How I'd draw it live (talk track)

  1. Start with the client & the ask — "users ask NL questions; expect bursty traffic." Draw the box, state QPS/latency targets to frame the rest.
  2. Edge: gateway + LB — TLS, routing, and rate-limiting first, so overload is shed at the door.
  3. Auth in two steps — OAuth/OIDC for who you are (JWT), then an ACL service for what you may see. Flag that this feeds retrieval filters (foreshadow the trap).
  4. Stateless app tier behind an LB — N replicas, autoscaled; call out that memory must move to Redis for this to work.
  5. Introduce the async path — queue + workers for the slow LLM call; explain the throughput/resilience win and the latency cost.
  6. Serving tier — vector DB + LLM serving + embeddings + cache. Name the LLM as the bottleneck and how caching/limits tame it.
  7. The RAG-authorization trap — spend real time here: filter-before-retrieve so context never contains forbidden rows. This is the differentiator most candidates miss.
  8. Ingestion & freshness — offline embed job, blue/green index swap.
  9. Wrap with observability & cost — OTel/Prometheus/Grafana/Splunk, per-tenant quotas. Close by restating the one or two trade-offs you'd revisit under different scale.

Phase 9 — the router is schema-driven The four routes above are no longer tied to a fixed domain. At load time schema.py infers each column's ROLE (identity / categorical / numeric / date / freetext) and persists a SchemaProfile to chroma_db/schema.json. The router's known-values AND its prompt are GENERATED from that profile, so "who earns the most" maps to the numeric Salary column with no hardcoded field names.

Why the guardrail (⑥) is the crux The LLM is great at reading intent ("Reyen" ≈ "Reyan") but can hallucinate a value that isn't in the data ("Vignesh" → a person who doesn't exist), which would filter to zero rows or fabricate a count. resolve_value() forces every proposed value back onto real stored data before any query runs — the LLM proposes, Python disposes.

3 · Phase-by-phase — what was built & learned

The project grew one phase at a time. Each card: the functionality added, the file/function it lives in, and the one key learning. Teal = a phase I built; purple = a question I chased down.

Built a phase Chased a question
0Setup
Environment & the local gate
scripts/check_gate.sh · certs/ · offline HF flags
Learning: a port can be open but not serving — verify the gate with real inference before debugging anything. Corporate SSL proxy means the embedding model must load fully offline.
1Data
Excel → Documents
data.py · load_employee_documents(), row_to_card()
Learning: embed a natural sentence (a "card"), not key-value text — models were trained on prose. Keep metadata separate for exact filtering. Fill blanks with "Unassigned".
2Index
Embeddings & the vector store
index.py · build_index(), get_store() · Chroma + MiniLM
Learning: the question must be embedded with the same model as the cards, or similarity is meaningless. Persist once to ./chroma_db; upsert by name so re-runs don't duplicate.
2·QAsked
Why semantic-only wasn't enough
learnings §1–2 · distance vs relevance scores
Learning: pure similarity is fuzzy and capped at k — it can't do "list ALL on MPLS" or "who reports to X". That gap is exactly what motivated hybrid retrieval.
3Retrieve
Hybrid routing (metadata vs semantic)
retrieval.py · detect_filter() → then llm_route() (3.5)
Learning: because the data is small & categorical, "does the question mention a known value?" is enough to choose an exact filter. 3.5: an LLM router handles typos/partials — but its value must be validated (resolve_value).
4Generate
The RAG loop completes
generate.py · answer(), build_messages(), get_llm()
Learning: augmentation = stuffing retrieved cards into the prompt. The single most important rule is the anti-hallucination grounding: answer only from the cards, else say "I don't know".
4.5Tone
Friendlier answers + honest sources
generate.py · SYSTEM_PROMPT, _cited_sources() (4.6)
Learning: warmth must not loosen grounding. 4.6: retrieval always returns k cards, so a "don't know" answer was citing unrelated names — cite only people the answer actually names.
5CLI
One front door
main.py · ask_loop() · open store once, fail gracefully
Learning: separate the ENGINE (answer()) from the UX. The CLI opens the store once, hides debug noise, and handles Ctrl-C / gate-down without a stack trace.
6Web UI
Streamlit front-end
app.py · @st.cache_resource, st.form
Learning: Streamlit reruns the whole script on every interaction — cache the slow store load, and batch input with a form. Same engine, new face: every earlier fix carries over for free.
7Count
Aggregation — the third route
retrieval.py · aggregate route · plan["count"] = len(docs)
Learning: LLMs are unreliable at counting. Make it a computation, not a generation: Python owns the number (len), the LLM only phrases it. Hard-guard the "count everyone" escape hatch.
8aDecompose
Multi-entity (compound) questions
retrieval.py · llm_decompose(), retrieve_multi() → generate._stitch()
Learning: one router returns one plan, so compound questions lost a half. Split into standalone sub-questions, route each through the same guardrail, then stitch the correct parts into one reply.
8a′Granularity
Answer only what was asked
generate.py · SYSTEM_PROMPT granularity rules
Learning: a one-field question ("who is X's manager?") should return one field, not the whole card. This is a presentation fix (prompt), unlike counting which was a computation fix.
8bMemory
Conversational memory (in-session)
main.py · history list · generate.build_messages(history=…)
Learning: memory has TWO jobs — generation memory (done: the LLM sees prior turns, so "whom am I?" works) and retrieval memory (not yet: routing still uses the raw question → query rewriting is next).
The through-line Every phase is the same pattern: find a real failure in the playground → understand why → fix it at the right layer (retrieval, computation, prompt, or UX). Counting was a computation bug; over-answering was a prompt bug; forgetting was a state bug. Same "wrong output" symptom, different cure each time.
