1 · Pure semantic search — what it can and can't do

I ran index.py and asked questions directly against the vector store.

My questionResultVerdict
"who does automation?"3 Automation people✓ correct
"who is vignesh's manager?"Vigneshwar + 2 random people, no actual answer✗ wrong

Why the split — what similarity_search actually does

  1. My whole question becomes one vector (a point in 384-dim space).
  2. Chroma returns the k cards whose vectors are closest to that point.
  3. That's it — no reasoning, no lookup. It matches the topic, not the intent.
My one-line takeaway Semantic search retrieves cards that are on the same topic as my question. It does not answer the question. "manager of vignesh?" returns Vigneshwar's own card (it's most "about" vignesh+manager) — the right data, but not the answer.

2 · Two confusions I cleared up

Confusion A — "why does it only print name + automation?"

It wasn't the retriever — it was the print() only showing 2 of 4 fields. The full Document always came back:

page_content: Vigneshwar B is managed by Rehan Sharma, works on the MTN project, specializing in Automation.
metadata:     {name, manager: Rehan Sharma, project: MTN, technology: Automation}

Fix: print all 4 fields + the full card + scores.

Confusion B — "then why won't it SAY Rehan?"

Because nothing reads the card yet. Retrieval fetches paper; it doesn't read it aloud. That reader is the LLM = Phase 4.

Mental model I locked in Retriever = librarian who fetches the right file but can't read it. Generator (LLM) = the person who reads it and answers. Two different jobs.

The scores — distance vs relevance

ColumnMeaningDirection
distanceraw L2 distance, question ↔ card vector (what Chroma ranks by)lower = closer = better
relevancenormalized 0..1 scorehigher = better
Trap I must remember A high score ≠ a right answer. "vignesh's manager" gave Vigneshwar's card a confident 0.355 — confidently the wrong thing. The score measures text similarity, not correctness. Read the gaps and ordering, not the absolute number.

3 · Hybrid routing — and how it really decides

Phase 3 added metadata filtering (exact where lookups) alongside semantic. The router picks one:

question → detect a KNOWN value in the text?
   ├─ yes → METADATA filter where {field: value}   (exact, COMPLETE "list all")
   └─ no  → SEMANTIC search top-k                   (fuzzy fallback)
The key correction to my first understanding I thought it "tries metadata, then falls back." True — but "found something" means an exact stored value appears verbatim in my question. It's a literal substring matcher, NOT an understander.

Proof from my own run — one word flips the route:

QuestionRouteWhy
"reports under Dhruv"SEMANTIC"Dhruv" ≠ stored "Dhruv Sharma"
"reports under Dhruv Sharma"METADATA (22)full value present

Also learned: an intent cue ("reports to" → manager) fixes the name-vs-manager clash, so "reports to Dhruv Sharma" returns her 22-person team, not Dhruv's own record.

BuiltPhase 4 · My finding

5 · The product flaw I found

My finding (verbatim intent) Users won't type exact names every time. So most questions fall back to semantic — and semantic is wrong for these. This won't hold up as a real product.

Confirmed — and it's actually TWO bugs:

BugEvidence from my run
1. Router misses partial names / variants"who reports under Reyan" → SEMANTIC → 3 people. "…Reyan Sharma" → METADATA → 20. Same question, one word.
2. Semantic can't do "list all" at all"skill of R & S" → semantic said "all four" — but there are 8. Capped at k, and confidently incomplete.
Why bug 2 is the scarier one Bug 1 gives too few results (visibly odd). Bug 2 gives a confident wrong "all" — the LLM doesn't know k=4 was just the cutoff. A wrong answer that looks right is worse than "I don't know."

6 · My fix ideas & the verdicts

Idea A — Token / partial string matching (match any word of a known value).

Partial win. Fixes partial names ("reyan" → Reyan Sharma), stays free & transparent. Does NOT fix typos ("reyen"). Small false-match risk on common words.

Idea B — Run semantic FIRST, then metadata-filter using a value extracted from the semantic hits.

Has a fatal flaw. Semantic returns whole cards ranked by fuzziness — the query's own subject (e.g. Reyan's own record, whose manager is Imran Nair) ranks #1, so I can't reliably pick which field/value to filter on. It just relocates the matching problem into the results, with added ambiguity. But the instinct — "fuzzy-resolve the entity, then exact-filter for completeness" — is correct. The fix is to fuzzy-match against the small known-value lists, not against the documents.

Idea C — Let the LLM decide the route (read query → output {route, field, value}).

Strongest idea — this is how production RAG does it. Tested live against the gate:

InputLLM router output
"reports under Reyan"manager = Reyan Sharma✓
"who works under reyen" (typo)manager = Reyan Sharma✓ fixed a typo!
"skill of R & S"technology = R&S (Routing & Switching)✓
"people in the airtel account"project = Airtel✓ synonym
"who keeps the network reliable?"semantic✓ chose semantic
"who is vignesh"name = "Vignesh"✗ hallucinated value
The catch I must remember The LLM can hallucinate a value not in the data ("Vignesh" ≠ stored "Vigneshwar B"). A wrong filter value → 0 results, silently. It also costs an extra LLM call and returns free text to parse.
The winning design (Idea C + a guardrail) Let the LLM do the understanding, but never trust its value blindly:
  • LLM proposes {route, field, value}.
  • Is value an exact known value? → use it.
  • Not exact? → fuzzy-snap to the nearest known value (difflib).
  • No close match? → fall back to semantic.
= LLM for intent/typos/synonyms + validation for guaranteed-real filter values.

My three approaches, side by side

ApproachTyposPartialsComplete "list all"RiskCost

✅ BUILT & VERIFIED (Phase 3.5): Idea C + guardrail is now the live router. Order: LLM router → rule-based detector → semantic (degrades gracefully if the gate is down). Real results: "reyen"→all 20, "R & S"→all 8, "vignesh"→fuzzy-snapped to "Vigneshwar B" (no 0-results), "airtel account"→Airtel.

7 · The interface — one front door

All the pieces (data → index → retrieval → generation) now sit behind a single command instead of scattered __main__ loops:

python src/main.py            # clean Q&A loop
python src/main.py --debug    # also show the routing decision per question

What main.py adds on top of the engine:

  • Opens the store once — embedding model + Chroma connection is the slow part, so do it a single time and reuse it for every question.
  • Debug is off by default — hides the [route] METADATA/SEMANTIC noise for a clean UX; --debug flips it back on for learning.
  • Fails gracefully — empty input just re-prompts; q/Ctrl-C/Ctrl-D quit without a traceback; a gate-down error says "Is the local Claude gate up? bash scripts/check_gate.sh" instead of a stack trace.

✅ VERIFIED end-to-end: "who reports to Dhruv Sharma?" → METADATA route → all 22 listed. "who keeps the network reliable?" → SEMANTIC → honest "I don't know based on the data" — the anti-hallucination guardrail choosing to say nothing rather than guess. That's the system being correct about its own limits, not broken.

8 · Inside embeddings — what the numbers really are

After the router, I wanted to see the actual numbers behind semantic search so it would stop feeling like magic. These are the questions I asked and what I found.

Q1. Can I see the embedding values the model produces for a card?

Yes. Each card becomes a fixed list of 384 numbers (this model = all-MiniLM-L6-v2, so 384 dimensions). Each number sits roughly between −1 and +1, and the whole vector is normalized to length ≈ 1.0.

# emb.embed_query("Vigneshwar B ... specializing in Automation.")
vector length (dimensions): 384
   dim[ 0] = -0.15004
   dim[ 1] = -0.00692
   dim[ 2] = -0.06062
   ... (381 more) ...
magnitude of the vector: 1.0   # MiniLM normalizes to ~1.0
Wording I had to fix It's not "training." The model was already trained by its makers. When we index, it only reads each card once and outputs a vector — that step is inference / encoding, a frozen text → 384 numbers function. Same input always gives the same output.

Q2. Are the 384 numbers "features of each word/token" that I can name?

No — two corrections in one.

  • Not per-word. The 384 numbers describe the whole card, not each word. (Internally the model makes a vector per token, then pools them into one sentence vector — that's what we store.)
  • Not nameable. There is no dim[7] = "seniority" or dim[42] = "automation". They are abstract learned axes ("latent dimensions") the model invented during its own training to keep similar sentences close and different ones far apart. Meaning lives in the pattern across all 384 together, never in one axis.
The map analogy that made it click A location is (latitude, longitude) — 2 numbers. Neither alone is "the city." Only together do they pin a spot. Embeddings are that same idea with 384 axes instead of 2.

Q3. Prove no single dimension = a human concept like "Automation".

I compared the top dims of two Automation cards (a, b) against a Wireless card (c). If a dimension were "the Automation feature", a & b would share a big value there and c would differ. They don't — the signal is scattered:

dima (Automation)b (Automation)c (Wireless)verdict
164−0.1592−0.0999−0.1133c sits between a & b → useless as a splitter
373+0.1504+0.0326−0.0800leans right, but a & b disagree a lot
227+0.1483+0.1591+0.0170closest to a theme, still not clean

No row cleanly says "these two are Automation, that one isn't." Yet cosine similarity across all 384 ranks a↔b high (~0.52) and a↔c low. Meaning is distributed, not localized.

Q4. So how does search actually compare two of these vectors?

Cosine similarity — the angle between vectors. 1.0 = same meaning, 0 = unrelated. It matches on meaning, not keywords:

# query: "who works on automation and scripting?"  (note: "scripting" is in NO card)
0.5259  Vigneshwar B ... Automation      #####################
0.5182  Nitesh Sharma ... Automation       ####################
0.1892  Aadhya Sharma ... Security        #######
0.1358  Aarush Sharma ... Wireless               #####
0.0373  The weather in Paris is cold.    #   # unrelated → ~0

The model scored the Automation people highest even though I asked about "scripting" — it understood scripting ≈ automation. That is the whole point of embeddings.

Why this justifies my hybrid router (the payoff) For "list everyone who reports to Dhruv Sharma", semantic scores are middling and have no clean cutoff (right people ~0.35–0.45, wrong people ~0.13–0.20). Semantic has no concept of "return ALL 22 and only those 22." A metadata filter where manager == "Dhruv Sharma" returns exactly 22, complete, guaranteed. Fuzzy meaning → semantic. Exact complete set → metadata.
Bonus term Extracting human-nameable concepts back out of these tangled vectors is a real research area (mechanistic interpretability, sparse autoencoders) — but the raw dimensions themselves stay unlabeled.

9 · Friendlier answers — without breaking the grounding

Playing in main.py --debug, I noticed the answers were correct but curt — the LLM basically re-read the card. I had two productization ideas:

  • Idea A — nicer tone: greet / thank / offer more help, so it feels like an assistant.
  • Idea B — instead of a flat "I don't know", let the LLM answer from its own knowledge.
The trap I nearly walked into (Idea B) My data has no "Balamurugan". If I let the model fall back to its own knowledge, it would happily explain the name — or worse, invent a fake employee ("Yes, Balamurugan reports to X"). That is hallucination — the exact thing RAG's guardrail exists to stop. In a data-lookup tool, a confident wrong answer is far more damaging than an honest "I don't have that."
ApproachVerdict
Strict flat "I don't know based on the data."Safe — but robotic
Free LLM fallback (Idea B, literally)❌ Invents fake employees — unacceptable
Middle ground: stay grounded, but phrase the "no" helpfully✅ What we shipped

The fix was prompt-only (no code logic change): rewrite SYSTEM_PROMPT in generate.py to be warm and keep every anti-hallucination rule. Key surviving line: Do NOT make up an answer from general knowledge.

Same 4 questions, before vs after:

QuestionBefore (curt)After (friendly, still grounded)
Is there an employee Pari?"Yes, Pari Sharma — managed by…""Yes! … Let me know if you'd like more details!"
How many under Aditya?"12 people work under…"Clean numbered list + "breakdown by project?"
what is 1+1?"I don't know based on the data.""1+1 is basic math… I can only help with facts about the team"
who is Balamurugan?"I don't know based on the data.""Could you double-check the spelling? … or search by manager / project / technology"
The lesson Tone lives in the prompt; grounding is non-negotiable. You can make a RAG bot as warm as you like by editing the system prompt — but the moment you let it answer from outside the retrieved records, it stops being a retrieval system and starts guessing. Change the wording of the "no", never the rule behind it. (Minor cost: "be warm" slightly invites filler — trim tone first if you ever want crisper answers.)

9.1 — The misleading-sources bug I caught

Testing the non-debug CLI, I asked "Hi what can you do?" and got a great capability answer — but it printed Sources (4): Advait Sharma, Kiara Sharma, …. Those 4 people had nothing to do with the answer.

Root cause — "sources" was a lie Semantic search always returns k=4 nearest cards, even for chitchat or an "I don't know". The code cited whatever retrieval fetched, not what the answer actually used. For metadata routes those are the same; for semantic they diverge and the citation becomes noise.

Fix (two filters, no extra LLM call), in generate.py _cited_sources():

  • Refusal guard — if the answer is a grounded "I don't have that" (or nothing was retrieved), cite nothing.
  • Mention filter — otherwise keep only retrieved people whose name appears in the answer (full name or first token, so "Pari" still credits "Pari Sharma").
QuestionRouteSources now
Hi what can you do?semanticnone (was 4 unrelated names)
Is there Pari?metadataPari Sharma
How many under Aditya?metadataall 12
who is Balamurugan?semanticnone (refusal)

Lesson: a citation must mean "the answer was built from this", not "retrieval happened to fetch this". Caveat: refusal detection is phrase-based (cheap heuristic) — reword the prompt heavily and you may need to add new cue phrases.

10 · How the LLM actually picks a search

I wanted to know: from natural language, how does it "call" one of the two searches?

The one sentence The LLM decides in words; my Python acts in code. The LLM never runs a search — it only returns a JSON label; retrieve()'s if/else reads that label and calls the search.

The flow for "who works under reyen":

# 1. llm_route(): the LLM reads the question + known vocab, RETURNS TEXT:
{"route":"metadata", "field":"manager", "value":"Reyan Sharma"}

# 2. Python parses it, guardrail snaps the value, returns ("manager","Reyan Sharma")

# 3. retrieve(): plain if/else — THIS is where a search is actually called
if hit:  store.get(where={field: value})          # METADATA (exact)
else:    store.similarity_search(question, k=k)    # SEMANTIC (fuzzy)
  • The LLM's whole job is turning messy language into a clean {route, field, value}.
  • The execution is dumb, deterministic Python — which is why it's reliable and why I can validate/override the LLM (the guardrail) before any search runs.
  • This is the hand-built version of what libraries call "tool / function calling" — same idea: model emits structured text, your code executes.

11 · Security, name matching & the "vicky" bug

11.1 — Are we sending all the data to the LLM?

No. The router prompt sends only the distinct categorical values — 7 managers, 9 projects, 12 technologies (~28 short labels). It does NOT send the 97 names or any who-reports-to-whom mapping. Full employee records reach the LLM only in the generation step, and only the handful retrieved for that one question — never the whole DB.

Why my setup is privacy-friendly The gate runs at localhost:8080, so data stays on my machine. The LLM is stateless — it reads, answers, forgets; it does not learn/memorize my data. Biggest productization risk = swapping the local gate for a CLOUD LLM — then PII + client project names cross the network boundary and you'd need a no-training guarantee, a DPA, and maybe redaction.

11.2 — If names aren't sent, how does "Vignesh" → "Vigneshwar B"?

Two different actors do two different jobs:

  • LLM (never sees names) → can only say "this is a name-type question", echoing the user's typed word as the value.
  • Python (has all 97 names locally) → resolve_value() snaps that word to the real name with difflib. The roster never leaves the machine.

11.3 — Name matching is difflib, NOT semantic search

difflib (names use this)Semantic (embeddings)
Comparesletters / charactersmeaning
Good attypos & partials of the same wordsynonyms, concepts
WherePython resolve_value()ChromaDB vectors

The name IS the primary key (unique id in Chroma). But matching is NOT "certain every time" — it has a hard 0.6 threshold. Real results:

'vigneshw'  -> Vigneshwar B   ✓
'vignesh'   -> Vigneshwar B   ✓
'vignsh'    -> None           ✗ (below 0.6 → falls to semantic)
'vig'       -> None           ✗ (too short)

Below the threshold it drops to semantic — which for a garbled name is unreliable (a name has no "meaning" to embed). It fails safely (won't invent a wrong person), but it does not always succeed. Robust fixes are a Phase 6 idea: phonetic matching (Soundex/Metaphone), or a smarter threshold.

11.4 — The "vicky" bug — and why it's NOT a breach or injection

What happened Asking "do you know vicky?" → difflib fails → semantic returns 4 random cards → the LLM recited them: "the employees I know about are Ayaan Sharma, Kiara…". Misleading, and it wrongly implied those were the only employees.
FearReality
Security breach?No — every name shown is in-scope data the user may query. Nothing leaked.
Prompt injection?No — that's a malicious hijack ("ignore your rules"). This was a normal query hitting a weak spot.
What it really isA relevance/quality bug — the LLM parroting irrelevant retrieved cards.

Note: the retriever ALWAYS returns k cards (even for meaningless queries). My earlier fix cleaned the Sources: line, but the LLM was still naming them inside the answer text.

The fix (Phase 4.6, prompt-only) Added a rule: the provided records may be irrelevant — use only ones that genuinely match; if none match, treat as "not found", never recite the others or imply they're the whole roster. Verified: "vicky" → clean "not found"; "vignsh" → still finds Vigneshwar B; "under Aditya" → still lists all 12.

11.5 — The "count" bug → a THIRD route (✅ built in Phase 7, see §13)

What happened "how many employees in total?" → no known entity → semantic → returned k=4 cards → the LLM counted those 4 and answered "4 employees". The real answer is 97.

Key realisation: counting is an aggregation, and neither semantic nor a plain metadata fetch is built to count. It's the same shape as "list everyone on MPLS" needing metadata not semantic — a whole question-category the current two routes miss.

Also a terminology fix I made for myself: the right behaviour is not "I can't disclose" (the total isn't secret) nor "I don't know" (the system does know) — it's to answer correctly: 97.

My plan (Phase 7): add a third route Extend llm_route() to also emit {route:"aggregate", operation:"count", field:…}, with a Python branch that does store.get(where=…) and returns the real count. This is lightweight tool-calling — the exact "LLM decides, Python executes" pattern I already built (§10). Full framework-based function-calling can come later for richer operations.

BuiltPhase 7 · Built

13 · Counting — the third route (aggregation)

The count bug from §11.5 is now fixed. I added a third route next to metadata & semantic:

metadata   -> exact filter, LIST the people        (existing)
semantic   -> fuzzy meaning search                  (existing)
aggregate  -> COUNT how many match, return a number  (NEW)
The golden rule of this phase The LLM must NEVER be the thing that counts — being bad at counting was the whole bug. Python owns the number (len(store.get(where=…))); the LLM only phrases it warmly. A count is just "do the metadata filter, then count the results instead of listing them."
QuestionRouteCount byAnswer
how many employees in total?aggregatefield=null → all97 (bug was "4")
how many under Aditya?aggregatemanager=Aditya12
how many on MPLS?aggregatetechnology=MPLS8
who reports to Dhruv?metadata—lists 22 (unchanged)

How it's wired (same "LLM decides, Python executes" pattern as §10):

  • Router prompt gained an "aggregate" option; llm_route() now returns a plan dict ({route, field, value}) instead of a bare tuple, so it can express "count everyone" (field=null) vs "count within a filter".
  • retrieve_with_plan() computes count = len(docs) in Python and puts it in the plan.
  • _answer_count() hands the LLM the exact number with "use this EXACTLY, do not recompute" — so tone stays friendly but the digit is Python's. Sources stay empty (a count names nobody).

13.1 — Following one question through the code

Trace "how many people work under Aditya?" end to end:

# 1. Router prompt now offers 3 routes. LLM reads the question, returns TEXT:
{"route":"aggregate", "field":"manager", "value":"Aditya"}

# 2. llm_route() validates it into a PLAN DICT (was a bare tuple before):
   - grand-total case ("how many in total?")  -> {route:aggregate, field:null, value:null}
   - else guardrail: resolve_value("Aditya") -> "Aditya Sharma"  (or None -> fallback)
   returns {route:"aggregate", field:"manager", value:"Aditya Sharma"}

# 3. retrieve_with_plan() does the COUNT — just len() of a metadata fetch:
   docs = store.get(where={manager:"Aditya Sharma"})   # the matching cards
   plan["count"] = len(docs)   # = 12  ← the number is BORN here, in Python
   returns (docs, plan)

# 4. answer() sees route==aggregate -> _answer_count():
   system prompt: "The exact count is 12. Use this number EXACTLY, do not recompute."
   LLM writes: "Aditya currently has 12 people working under her. Want a breakdown?"
The key architectural insight An aggregate is literally a metadata filter that we len() instead of list — same store.get(where=…), different final step. That's why it was cheap to add: the retrieval machinery already existed, and the anti-hallucination guardrail is reused, not rebuilt (aggregate values pass through the same resolve_value() snap as metadata).

What made it possible: widening llm_route()'s return from a tuple (field, value) to a plan dict {route, field, value}. A tuple couldn't say "count everyone, no field"; the dict lets one router express three intents (list / count-all / count-filtered) with no new plumbing.

Design choices I made (1) Right behaviour for "how many?" is not "I can't disclose" (not secret) nor "I don't know" (it knows) — it's the real number. (2) Scope kept to single counts (total + filtered); group-by tables ("how many per manager?") are a later extension. (3) Graceful fallback holds: with the LLM router off, aggregate isn't available, so counts safely degrade to semantic — no crash.
BuiltPhase 8a · Built

14 · Query decomposition (multi-entity questions)

Playground finding: a compound question got half-answered.

# asked ONE line with TWO intents:
"list no of people under Aditya AND tell me who is Vivek Sharma?"
  -> only Vivek was answered; the count was silently dropped.
Root cause llm_route() returns exactly one plan {route, field, value}. So the architecture could physically answer only one intent per turn — the second half had nowhere to go.

The fix — query decomposition (a real RAG technique): split the question into standalone sub-questions, route each through the SAME machinery, then stitch the answers.

question
  -> llm_decompose()   # ["how many under Aditya?", "who is Vivek?"]
       │
       ├─ sub 1 -> llm_route() -> resolve_value() -> AGGREGATE -> count 12
       └─ sub 2 -> llm_route() -> resolve_value() -> METADATA  -> Vivek's card
       │
  -> _stitch()   # one warm reply containing BOTH answers

Why reuse, not rebuild: each sub-question flows through the existing llm_route() / resolve_value() guardrail. A simple (non-compound) question decomposes to a 1-element list, so retrieve_multi() takes the unchanged single path — old behaviour is byte-for-byte identical.

It also fixes consistency for partial names "under Vihaan" is now its own sub-question, always routed through resolve_value(), which fuzzy-snaps "Vihaan" → the real manager "Vihaan Sharma" (→ 14). Before, the same query sometimes resolved and sometimes fell to semantic ("no records") — a flaky false-negative. Routing every sub through one guardrail makes resolution deterministic. (Note: 14 was always the correct number — the earlier "no records" was the bug, not the count.)
Design choices I made (1) Reuse over reinvent: llm_route_many loops the existing router; no parallel resolver. (2) Graceful all the way down: gate off → llm_decompose returns None → single path → rule-based → semantic, exactly as before. (3) Tone tweak: only suggest "check the spelling" when NO record matched — a correct fuzzy match no longer nags. (4) Cost is visible: a compound question = 1 decompose + N route + N phrasing + 1 stitch LLM calls; fine for learning, a cheaper variant just joins sub-answers with blank lines.

14.1 — Answer only what was asked (granularity)

Next playground finding: asking for ONE field returned the WHOLE card.

"who is manager of Vignesh?"
  before -> "...managed by Rehan, works on MTN, specializes in Automation"  # all 3 fields
  after  -> "...manager is Rehan Sharma."                                # just the field asked
Why it was NOT a tool-calling problem Retrieval & routing were perfect — the right person was found. The over-answer happened in GENERATION: format_cards() feeds the LLM the full card, and the old prompt never said "answer only the field asked". A tool would hand back the same full card, so tool calling fixes nothing here. Counting was a computation bug (Python fixed it); this is a presentation bug (the prompt fixes it). Same "extra stuff" symptom, opposite cure.

14.2 — Stitching the pieces back into ONE reply

Decomposition splits a compound question into sub-questions and answers each on its own. But returning three separate blobs feels robotic — so a final step recombines them.

"who is Pari's manager and how many are on MTN?"
  split   -> [ "who is Pari's manager?",  "how many are on MTN?" ]
  answer  -> [ "Aditya Sharma",           "12 people" ]        # each sub answered alone
  stitch   -> "Pari reports to Aditya Sharma, and there are 12 people on MTN."  # one warm reply
The stitch is deliberately dumb — and that's the point _stitch() is given ONLY the already-correct sub-answers and told: combine them, add NO new facts, recompute NO number, drop NO part. It never re-touches the data or the count — those were already settled by retrieval/Python. A cheaper "\n\n".join(...) would work; the LLM stitch just reads warmer for a compound question. Keeping it fact-blind is what stops it re-introducing a hallucination after all the careful grounding upstream.
History threads through EVERY sub-answer (Phase 8b tie-in) Once conversational memory landed (§15), the compound path had to respect it too: history is forwarded into each sub-call's build_messages() (via _answer_one), so "what about his project?" inside a compound question still resolves "his" from earlier turns. The _stitch step itself stays history-free — it only combines parts that are already correct.

15 · Conversational memory (in-session history)

Playground finding: the bot had no memory — every turn answered from scratch.

"I am vignesh"   -> finds Vigneshwar B        # ✓
"whom am I?"     -> "I don't have info about you"  # ✗ forgot turn 1
Root cause build_messages() returned a fresh [system, human] list with ONLY the current question; nothing stored or replayed prior turns. Stateless was fine for independent lookups but breaks any back-reference.

The fix: the CLI keeps a running history of prior turns and threads it into the prompt, slotted BETWEEN the system rules and the current turn:

[ system rules ]
[ ("human","I am vignesh"), ("ai","...Vigneshwar B...") ]   # history
[ retrieved cards + current question ]                       # this turn
Memory has TWO jobs — we did one Generation memory ✓ — the LLM now SEES prior turns, so "who is his manager?" resolves "his" from history and answers correctly. Retrieval memory ✗ — the router still routes on the RAW question, so "whom am I?" fetches random cards (no known entity). Generation memory rescues it (the answer leans on history), but a follow-up whose retrieval matters would miss. Making retrieval follow-up-aware = query rewriting ("his project" → "Pari's project" before retrieval) — the next step.
Design choices I made (1) Backwards-compatible: history is an optional kwarg (default None) — the Streamlit app, which doesn't pass it, stays stateless with zero changes. (2) Capped to the last 6 turns so a long chat doesn't bloat the prompt. (3) reset command clears it (and proves the memory was real). (4) Prompt reconciled: the "use ONLY the records" grounding rule was fighting history (the model distrusted it) — reworded to "records AND facts established earlier in THIS conversation", with "not found" only when NEITHER has the answer. (5) In-session only — lost on restart; persistence is later.

Quick glossary (for fast revision)

  • Embedding — text → a vector capturing meaning; lets us search by meaning, not keywords.
  • Dimension / latent feature — one of the 384 numbers in a vector. Abstract & unnameable; meaning lives in all of them together.
  • Inference / encoding — the model reading a card and outputting its vector. NOT training (the model is already trained & frozen).
  • Cosine similarity — angle between two vectors. 1.0 = same meaning, 0 = unrelated. How semantic ranking works.
  • difflib fuzzy-snap — Python CHARACTER similarity (not semantic) that maps a typed value to the closest real one, above a 0.6 threshold. Used for name/value matching, all local.
  • Tool / function calling — pattern where the LLM emits structured text (a route/args) and YOUR code executes. We built it by hand in llm_route().
  • Prompt injection — a MALICIOUS input trying to hijack the system's instructions. Not the same as a normal query hitting a weak spot.
  • Vector store (Chroma) — DB that finds nearest vectors; persisted to ./chroma_db.
  • Semantic search — closest-vector match. Fuzzy; capped at k; can't do "list all".
  • Metadata filter — exact where={field:value} match. Complete; needs the exact value.
  • Retrieval — finding the right cards. Generation — LLM reading them to write the answer.
  • Augmentation — stuffing retrieved cards into the prompt (the "A" in RAG).
  • Grounding — answer uses only provided data; else "I don't know" (anti-hallucination).
  • LLM-as-router — using the LLM to choose the retrieval strategy; validate its output against known values.
