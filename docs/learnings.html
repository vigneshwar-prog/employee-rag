Phase 2 · Playground

1 · Pure semantic search — what it can and can't do

I ran index.py and asked questions directly against the vector store.

My questionResultVerdict
"who does automation?"3 Automation people✓ correct
"who is vignesh's manager?"Vigneshwar + 2 random people, no actual answer✗ wrong

Why the split — what similarity_search actually does

  1. My whole question becomes one vector (a point in 384-dim space).
  2. Chroma returns the k cards whose vectors are closest to that point.
  3. That's it — no reasoning, no lookup. It matches the topic, not the intent.
My one-line takeaway Semantic search retrieves cards that are on the same topic as my question. It does not answer the question. "manager of vignesh?" returns Vigneshwar's own card (it's most "about" vignesh+manager) — the right data, but not the answer.
Phase 2 · Playground

2 · Two confusions I cleared up

Confusion A — "why does it only print name + automation?"

It wasn't the retriever — it was the print() only showing 2 of 4 fields. The full Document always came back:

page_content: Vigneshwar B is managed by Rehan Sharma, works on the MTN project, specializing in Automation.
metadata:     {name, manager: Rehan Sharma, project: MTN, technology: Automation}

Fix: print all 4 fields + the full card + scores.

Confusion B — "then why won't it SAY Rehan?"

Because nothing reads the card yet. Retrieval fetches paper; it doesn't read it aloud. That reader is the LLM = Phase 4.

Mental model I locked in Retriever = librarian who fetches the right file but can't read it. Generator (LLM) = the person who reads it and answers. Two different jobs.

The scores — distance vs relevance

ColumnMeaningDirection
distanceraw L2 distance, question ↔ card vector (what Chroma ranks by)lower = closer = better
relevancenormalized 0..1 scorehigher = better
Trap I must remember A high score ≠ a right answer. "vignesh's manager" gave Vigneshwar's card a confident 0.355 — confidently the wrong thing. The score measures text similarity, not correctness. Read the gaps and ordering, not the absolute number.
Phase 3 · Playground

3 · Hybrid routing — and how it really decides

Phase 3 added metadata filtering (exact where lookups) alongside semantic. The router picks one:

question → detect a KNOWN value in the text?
   ├─ yes → METADATA filter where {field: value}   (exact, COMPLETE "list all")
   └─ no  → SEMANTIC search top-k                   (fuzzy fallback)
The key correction to my first understanding I thought it "tries metadata, then falls back." True — but "found something" means an exact stored value appears verbatim in my question. It's a literal substring matcher, NOT an understander.

Proof from my own run — one word flips the route:

QuestionRouteWhy
"reports under Dhruv"SEMANTIC"Dhruv" ≠ stored "Dhruv Sharma"
"reports under Dhruv Sharma"METADATA (22)full value present

Also learned: an intent cue ("reports to" → manager) fixes the name-vs-manager clash, so "reports to Dhruv Sharma" returns her 22-person team, not Dhruv's own record.

Phase 4 · My finding

5 · The product flaw I found

My finding (verbatim intent) Users won't type exact names every time. So most questions fall back to semantic — and semantic is wrong for these. This won't hold up as a real product.

Confirmed — and it's actually TWO bugs:

BugEvidence from my run
1. Router misses partial names / variants"who reports under Reyan" → SEMANTIC → 3 people. "…Reyan Sharma" → METADATA → 20. Same question, one word.
2. Semantic can't do "list all" at all"skill of R & S" → semantic said "all four" — but there are 8. Capped at k, and confidently incomplete.
Why bug 2 is the scarier one Bug 1 gives too few results (visibly odd). Bug 2 gives a confident wrong "all" — the LLM doesn't know k=4 was just the cutoff. A wrong answer that looks right is worse than "I don't know."
My ideas · Verdicts

6 · My fix ideas & the verdicts

Idea A — Token / partial string matching (match any word of a known value).

Partial win. Fixes partial names ("reyan" → Reyan Sharma), stays free & transparent. Does NOT fix typos ("reyen"). Small false-match risk on common words.

Idea B — Run semantic FIRST, then metadata-filter using a value extracted from the semantic hits.

Has a fatal flaw. Semantic returns whole cards ranked by fuzziness — the query's own subject (e.g. Reyan's own record, whose manager is Imran Nair) ranks #1, so I can't reliably pick which field/value to filter on. It just relocates the matching problem into the results, with added ambiguity. But the instinct — "fuzzy-resolve the entity, then exact-filter for completeness" — is correct. The fix is to fuzzy-match against the small known-value lists, not against the documents.

Idea C — Let the LLM decide the route (read query → output {route, field, value}).

Strongest idea — this is how production RAG does it. Tested live against the gate:

InputLLM router output
"reports under Reyan"manager = Reyan Sharma✓
"who works under reyen" (typo)manager = Reyan Sharma✓ fixed a typo!
"skill of R & S"technology = R&S (Routing & Switching)✓
"people in the airtel account"project = Airtel✓ synonym
"who keeps the network reliable?"semantic✓ chose semantic
"who is vignesh"name = "Vignesh"✗ hallucinated value
The catch I must remember The LLM can hallucinate a value not in the data ("Vignesh" ≠ stored "Vigneshwar B"). A wrong filter value → 0 results, silently. It also costs an extra LLM call and returns free text to parse.
The winning design (Idea C + a guardrail) Let the LLM do the understanding, but never trust its value blindly:
  • LLM proposes {route, field, value}.
  • Is value an exact known value? → use it.
  • Not exact? → fuzzy-snap to the nearest known value (difflib).
  • No close match? → fall back to semantic.
= LLM for intent/typos/synonyms + validation for guaranteed-real filter values.

Quick glossary (for fast revision)

  • Embedding — text → a vector capturing meaning; lets us search by meaning, not keywords.
  • Vector store (Chroma) — DB that finds nearest vectors; persisted to ./chroma_db.
  • Semantic search — closest-vector match. Fuzzy; capped at k; can't do "list all".
  • Metadata filter — exact where={field:value} match. Complete; needs the exact value.
  • Retrieval — finding the right cards. Generation — LLM reading them to write the answer.
  • Augmentation — stuffing retrieved cards into the prompt (the "A" in RAG).
  • Grounding — answer uses only provided data; else "I don't know" (anti-hallucination).
  • LLM-as-router — using the LLM to choose the retrieval strategy; validate its output against known values.
