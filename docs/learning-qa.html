Lesson 001: BM25 Retriever

Date: 2026-07-24

What It Is

BM25 is a keyword-based retrieval algorithm. It ranks documents by how well their words match the query words.

How It Scores (Simple)

  • Higher score if important query words appear in a document.
  • Higher score for rare words (rare words are more informative).
  • Controls document length so very long text does not always win.

Why It Is Useful

  • Fast and reliable when query words and data words are similar.
  • No embeddings required.
  • Great for exact terms like names, project labels, and technologies.

Limitation

BM25 does not understand meaning like embeddings do. If query uses synonyms not present in data text, BM25 can miss good results.

Interview-Ready One-Liner

BM25 is a lexical ranking function that retrieves documents using keyword relevance, balancing term frequency, inverse document frequency, and length normalization.

Checkpoint Questions

  1. If query and data use different words with same meaning, which works better: BM25 or vector retrieval? Why?
  2. Why should long documents not automatically get higher relevance scores?

Lesson 002: Embedding Model Options for This Project

Date: 2026-07-24

What Is an Embedding Model?

An embedding model converts text into a numeric vector so we can compare meaning using vector similarity search.

Options We Can Use Here

  • text-embedding-3-small (through local gate at localhost:8080): ideal when gate embeddings endpoint is healthy.
  • text-embedding-ada-002 (through local gate): older option if served by the same embeddings endpoint.
  • all-MiniLM-L6-v2 (local sentence-transformers): reliable local option when gate embeddings are unavailable.

Quick Comparison

  • Quality: text-embedding-3-small is usually better than ada-002 for modern retrieval use cases.
  • Operational simplicity: gate-based models are easiest only when the embeddings endpoint works in your environment.
  • Reliability: all-MiniLM-L6-v2 runs locally and avoids dependency on gate embeddings availability.
  • Project fit: with only about 97 rows, all three can work; hybrid retrieval design matters more than tiny embedding differences.

Recommended Choice

Current project decision: use all-MiniLM-L6-v2 as primary because gate embeddings are not working in your setup.

Interview-Ready One-Liner

For this environment, I selected all-MiniLM-L6-v2 because it is stable and local; with a small structured dataset, hybrid retrieval design contributes more to accuracy than switching embedding providers.

Checkpoint Questions

  1. Why is all-MiniLM-L6-v2 a practical choice for your current environment?
  2. If the gate embeddings endpoint starts working later, what benchmark would you run before switching back?
  3. For this dataset, why does hybrid retrieval matter more than changing embedding models?

Lesson 003: Triple-Hybrid Retrieval for This Project

Date: 2026-07-25

What Is Triple-Hybrid Retrieval?

A retrieval strategy that combines three independent ranking methods:

  • Semantic search: embed question → find employees with similar meaning (captures intent).
  • Keyword search (BM25): exact word matching → find employees with query terms (captures specificity).
  • Metadata filtering: exact categorical match → find employees by manager/project/tech (captures set queries).

Why All Three for Your Dataset?

  1. Semantic alone misses exact terms: "List everyone on MPLS" — embeddings might find networking people but not guarantee MPLS exactly.
  2. Keyword alone misses intent: "Who handles network resilience?" — BM25 fails if data says "redundancy" not "resilience".
  3. Metadata alone is inflexible: "Tell me about the Cisco team" — no metadata column for "Cisco", but semantic+keyword find it.

How They Work Together (Example)

Query: "Who works on MPLS projects?"

  • Semantic: "MPLS", "projects", "work" → embeddings find people with similar job descriptions.
  • Keyword (BM25): exact match on "MPLS" and "projects" in employee cards.
  • Metadata: filter by `technology == "MPLS"` (exact).
  • Merged result: rank by combined score; top results appear in both semantic + keyword, OR match the metadata filter.

Implementation Pattern

In LangChain:

  • Create a semantic_retriever (embeddings + Chroma similarity).
  • Create a keyword_retriever (BM25 on the same documents).
  • Create a metadata_retriever (Chroma with `where` filters).
  • Combine all three with a EnsembleRetriever (merge + deduplicate + re-rank).

Interview-Ready One-Liner

For this dataset, triple-hybrid retrieval (semantic + keyword + metadata) ensures exact set queries work (metadata), synonyms are caught (semantic), and proper terms are emphasized (keyword), which pure semantic search alone cannot guarantee.

Checkpoint Questions

  1. Why does BM25 fail on "Who handles network resilience?" if the data says "redundancy"?
  2. If you only used semantic search, would "List everyone on MPLS" return all 6 MPLS people? Why or why not?
  3. In the triple-hybrid design, which retriever should run first, and why does order matter for merging?

Lesson 004: Semantic vs Keyword vs Metadata — Deep Comparison

Date: 2026-07-25

Three Retrieval Methods Explained

1. Semantic Search (Embeddings)

How it works: Converts text to a vector (384 numbers for all-MiniLM-L6-v2). Finds employees with similar vectors using cosine similarity.

Example query: "Who handles network resilience?"

  • Your query is converted to vector: [0.2, -0.5, 0.8, ...]
  • Each employee card is also a vector: [0.19, -0.48, 0.82, ...]
  • Similarity = dot product / (magnitude1 × magnitude2) = 0.99 (very close!)
  • Result: Returns employee cards about "redundancy", "failover", "high availability" because they are semantically similar to "resilience".

Pros: Catches synonyms, understands meaning, flexible intent.

Cons: May rank irrelevant results high if they are semantically close; cannot enforce exact matching.

2. Keyword Search (BM25)

How it works: Scores documents by exact word overlap. Rare words score higher. Document length normalized.

Example query: "List everyone on MPLS"

  • Query terms: ["List", "everyone", "on", "MPLS"]
  • Employee card 1: "Ishan works on MPLS, specializes in routing" → contains "MPLS" (1 hit, rare word = high score)
  • Employee card 2: "Alice on Cloud Networking" → no match (0 hits, low score)
  • Result: Returns ALL employees mentioning "MPLS" exactly, ranked by frequency and rarity.

Pros: Exact term matching, high precision on proper nouns, fast.

Cons: Fails on synonyms ("resilience" vs "redundancy"), requires exact word presence.

3. Metadata Filtering (Chroma `where`)

How it works: Exact categorical lookup. Returns only records matching a filter.

Example query: "Who reports to Dhruv Sharma?"

  • Extract manager name from query (if recognized): "Dhruv Sharma"
  • Filter: `where={"manager": "Dhruv Sharma"}`
  • Result: Returns ALL 8 employees managed by Dhruv, guaranteed 100% recall.

Pros: Perfect precision/recall on structured fields, instant.

Cons: Only works for known categorical values, no flexibility, inflexible for natural language.

Comparison Table

Aspect Semantic Keyword (BM25) Metadata Filter
Speed Slow (vector search over 97 rows) Fast (inverted index) Instant (hash lookup)
Handles Synonyms? ✅ Yes ❌ No N/A (not applicable)
Exact Recall? ❌ Maybe (miss edge cases) ✅ Yes (if term exists) ✅ 100% (if filter applies)
Best For Intent, natural language, open-ended Proper nouns, exact terms Set queries (list all X)
Fails On "List all MPLS people" (incomplete) "Resilience" when data says "redundancy" Any natural language query

Real Query Examples from Your Dataset

Query A: "Who works on MPLS?"

  • Semantic: ⚠️ Returns 5 out of 6 MPLS people (misses one with different wording).
  • BM25: ✅ Returns all 6 (exact match on "MPLS").
  • Metadata: ✅ Returns all 6 (exact match on technology column).
  • Winner: BM25 or metadata alone work; semantic is weak.

Query B: "Tell me about our redundancy experts"

  • Semantic: ✅ Finds people with keywords like "failover", "resilience", "ha" (understands intent).
  • BM25: ❌ Returns nothing (data says "resilience" not "redundancy").
  • Metadata: ❌ No such column (not applicable).
  • Winner: Semantic alone works; BM25 fails.

Query C: "Who reports to Dhruv Sharma?"

  • Semantic: ❌ Returns people who sound like they might (may include false positives).
  • BM25: ~ Matches "Dhruv" and "Sharma" in cards, but also returns others mentioning her.
  • Metadata: ✅ Exact match: `where={"manager": "Dhruv Sharma"}` → all 8 direct reports.
  • Winner: Metadata filter guarantees precision.

Why Triple-Hybrid Is Optimal

Each retriever covers cases the others fail on. By combining all three and merging results:

  • Semantic catches intent (resilience = redundancy).
  • BM25 catches exact terms (MPLS = MPLS).
  • Metadata catches set queries (all people under Dhruv).
  • Merge via union (OR logic): return unique results ranked by how many retrievers found them.

Interview-Ready One-Liner (Updated)

Semantic search captures intent and synonyms, BM25 ensures exact terms are found, and metadata guarantees set queries; triple-hybrid combines them because each fails uniquely on query patterns the others handle well.

New Checkpoint Questions

  1. Why would "List all MPLS people" fail with only semantic search?
  2. If you only used metadata filters, how would you answer "Tell me about our resilience work"?
  3. Why is union (OR) the right merging strategy instead of intersection (AND)?
  4. For the query "Tell me who currently reports to Dhruv and has MPLS experience," which parts should be hard metadata constraints and which parts should be semantic/keyword evidence?
  5. If the user asks "people with MPLS experience" instead of "current MPLS engineers," should you still hard-filter technology == "MPLS" or relax it? Why?
  6. For the query "List all people under Dhruv with MPLS experience," how would you define: (1) hard constraints, (2) soft ranking signals, and (3) final answer formatting with sources?

Lesson 005: Scaling from a Small Excel to a Huge RFC / Document Corpus

Date: 2026-07-26 · Interview question

The Question

"You built this over an Excel sheet. What if instead you had a huge collection of RFC papers and reference links — how would the approach change?"

The Key Insight (lead with this)

The Excel design works because the data is small, structured, and categorical — 97 clean rows with fixed fields. That is what let me treat one row = one document and do exact metadata filtering. RFC papers break all of those assumptions, so the architecture shifts from "one row = one document" to a chunking + embedding pipeline. The hybrid + metadata instinct stays right; it just scales up.

What Changes, Step by Step

  1. Parsing: Excel was already structured. RFCs are long semi-structured text (PDF/HTML/txt) + links → use loaders (PyPDF, Unstructured) that extract clean text and preserve structure (RFC number, title, section headings).
  2. Chunking — the big new step: a 40-page RFC can't be one vector (token limits; one embedding averages away all meaning). Split into chunks (~500–1000 tokens, 10–15% overlap so a boundary-split sentence isn't lost). Now one chunk = one document.
  3. Metadata per chunk: attach {rfc_number, title, section, url, status} to every chunk — this is the Excel instinct surviving: "find this in RFC 2616 §14" becomes a metadata filter, just like "manager == Dhruv Sharma".
  4. Approximate retrieval: 97 rows → millions of chunks. Brute-force similarity dies; use an ANN index (HNSW/IVF) in a real vector DB.
  5. Hybrid matters even more: RFCs are full of exact identifiers ("RFC 5246", "TLS 1.2", header names) → keyword/BM25 nails those where pure embeddings fumble.
  6. Re-ranking: huge corpora give noisy top-k → add a cross-encoder re-ranker to reorder top ~50 down to the best ~5 before the prompt. (Small Excel didn't need this.)
  7. References / links: store each link as source metadata for citations; or go further with GraphRAG — model RFC→RFC references as a graph so "what does RFC X depend on?" is a traversal, not a similarity search.

Trade-offs to Say Out Loud

  • Chunk size: small = precise but context-poor; large = more context but noisier, diluted embeddings. Overlap helps but costs storage.
  • Cost / latency: millions of chunks → embedding cost, storage, ANN tuning; the re-ranker adds a second model hop.
  • Freshness: RFCs get obsoleted → carry status: "obsoleted by RFC N" in metadata or you surface stale answers.

Interview-Ready One-Liner

Excel let me treat one row as one document with clean metadata. A large RFC corpus flips that — the work moves into a chunking + embedding pipeline with metadata per chunk, an ANN-backed hybrid index, and a cross-encoder re-ranker; the hybrid-and-metadata instinct from the small project is exactly right, it just scales up with chunking and approximate search.

Checkpoint Questions

  1. Why can't you embed a whole 40-page RFC as a single vector — what two problems does chunking solve?
  2. Why does hybrid (keyword + semantic) matter more for RFCs than it did for the Excel sheet?
  3. What does a cross-encoder re-ranker add that ANN vector search alone doesn't — and why didn't the Excel project need one?
  4. How would you stop the system from answering with an RFC that has been obsoleted?

Lesson 006: Temperature in an LLM

Date: 2026-07-26

What It Is

When an LLM generates a token it produces a probability distribution over all possible next tokens. Temperature is a knob that reshapes that distribution before a token is sampled. Mechanically, the raw scores (logits) are divided by the temperature before the softmax: dividing by a small number exaggerates the gaps (winner takes all); dividing by a big number flattens them (everything gets a chance).

  • Low (→ 0): sharpens the distribution → deterministic, predictable (same prompt → same answer).
  • High (→ 1 and above): flattens the distribution → varied, creative, riskier (same prompt → different answers).

Simple Example

After "The network protocol is", suppose the base probabilities are TCP 0.70, UDP 0.20, "banana" 0.001:

  • temp = 0 → picks "TCP" every time; the rest are silenced.
  • temp = 0.7 → usually "TCP", sometimes "UDP" — natural variety.
  • temp = 1.5 → "TCP"/"UDP" often, but now "banana" has a real shot → creative but can derail.

Why It Matters in This Project

Every LLM call in generate.py and retrieval.py uses temperature=0. That is the correct choice because:

  1. It's a factual lookup, not a creative tool — "who is X's manager?" has one right answer; I want the same correct answer every time.
  2. The router emits JSON — llm_route() needs stable, parseable {route, field, value}; higher temp risks the model breaking the format.
  3. Grounding / anti-hallucination — higher temp increases the chance the model wanders off the retrieved cards, the opposite of what a grounded RAG wants.

When You'd Raise It

  • Factual Q&A, routing, extraction, JSON (this project): 0 – 0.3 — correctness & determinism.
  • Summaries, rephrasing, chat: ~0.5 – 0.7 — natural but grounded.
  • Brainstorming, creative copy, name ideas: ~0.8 – 1.2 — you want variety.

Two Things People Mix Up

  • Temperature vs. top-p (nucleus sampling): both control randomness. Temperature rescales all probabilities; top-p instead truncates to the smallest set of tokens whose probability sums to p (e.g. 0.9) and samples among those. Usually tune one, not both.
  • temp 0 ≠ perfectly deterministic: it's effectively deterministic, but floating-point/hardware and load-balanced backends can still vary occasionally.

Interview-Ready One-Liner

Temperature scales the logits before sampling — low temperature sharpens toward the top token (deterministic, factual), high temperature flattens the distribution (creative, varied). I use 0 across my RAG system because it's a factual lookup with JSON routing and strict grounding, where I want the same correct answer and stable output every time.

Checkpoint Questions

  1. Mechanically, what does dividing the logits by the temperature do to the gaps between token scores?
  2. Why would temperature=0 be the safest setting for the JSON router in llm_route()?
  3. What's the difference between temperature and top-p, and when might you reach for top-p instead?
  4. Give one task where you'd deliberately set a high temperature — and why it's fine there but wrong for this project.
