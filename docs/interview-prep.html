MAPREFERENCE · FULL PIPELINE REFERENCE

System Architecture Diagram — ingestion pipeline (Excel → chunk → embed → vector store) feeding into the query pipeline (question → route → guardrail → retrieve → augment → generate → cite).

HAND-DRAWN OVERVIEW

Top lane is ingestion: an uploaded spreadsheet gets a column-by-column schema classification, then each row becomes its own chunk (one prose "card" per employee), gets embedded locally, and lands in a persistent Chroma store. Bottom lane is the query path: a question is routed to one of four retrieval strategies, guarded against hallucinated filter values, retrieved, augmented into a grounded prompt, generated by the same local Claude gate, and trimmed to only the citations actually used before reaching the user. The dashed diagonal shows the vector store from ingestion directly feeding the retrieval step in the query pipeline — the two lanes share one store.

Q1DESIGN RATIONALE · OPENER PARTIAL

Walk me through your project in 60 seconds. Why a hybrid retriever instead of pure vector search? Give a query semantic search gets wrong — and explain why the embedding fails on it.

YOUR ANSWER
"RAG pipeline to fetch employee data — project, manager, techstack. Data ingestion from Excel, each employee card as a single chunk, embedding with all-minilm-l2v2, stored vectors in vector DB. For retrieval I used semantic search plus metadata filtering, then used retrieved data to generate a grounded response. Vector search doesn't work well with quantifying numbers such as 'give me the count of employees' or 'give me the list of MPLS employees' — there metadata filtering works good. It fails because the embedding model can just give first k matching semantic results, so it cannot count values."
WHAT YOU GOT RIGHT
  • Pipeline sequence was accurate and well-ordered — ingestion → chunk → embed → store → hybrid retrieve → grounded generate. Said alone, this passes.
  • Chunking choice is defensible. One employee = one chunk = one atomic entity means no person's facts split across a boundary. Frame it as a decision, not a default.
  • The core insight is present — you know counting and complete-list queries need filtering, not similarity. That's the thesis of the project and you led with it.
GAP 1 — MODEL NAME

You said all-minilm-l2v2. It is all-MiniLM-L6-v2. The L6 = 6 transformer layers. Small slip, but model names are a credibility signal — fumbling it reads as "copied from a tutorial." Keep the justification loaded:

384 dimensions, runs on CPU with no API cost, and for 97 short cards the quality gap versus a large embedding model is negligible.
GAP 2 — YOU GAVE THE SYMPTOM, NOT THE MECHANISM

"It gives the first k matching results so it cannot count" describes what happens. The interviewer's next word is "but why?" Two mechanisms answer it:

① Vector search is a top-K nearest-neighbour operation. K is a parameter you fix before you know the answer. Counting requires a complete set. You cannot get a complete set from an operation whose size you had to choose in advance.

And the deeper one, which separates a strong candidate from an average one:

② Embeddings encode topical similarity, not attribute equality. A card reading "Manager is Dhruv Sharma" and one reading "Manager is Anika Sharma" sit very close in vector space — both are short prose about a manager. The embedding captures "this is a sentence about management"; it does not encode "this string equals Dhruv." Exact identity is a symbolic property, and dense vectors are lossy compression that discards symbolic precision.
GAP 3 — YOUR TWO EXAMPLES ARE DIFFERENT FAILURES

You grouped "count" and "list all MPLS" together. They're related but distinct — separating them demonstrates precision:

QUERY TYPEWHAT BREAKSYOUR ROUTE
"List everyone on MPLS"Completeness — K truncates the set metadata → Chroma where
"How many on MPLS?"Completeness + arithmetic — LLMs miscount lists aggregate → len() in Python

The second needs an extra guarantee: even handed all 12 cards, an LLM asked to count can say 11. That is why _aggregate() computes in Python and passes the finished number to the model. Your own code comment is the best line here — "never trust the LLM to do math."

REHEARSED VERSION
"It's a natural-language Q&A system over an employee spreadsheet — 97 people, with columns for manager, project, and technology. Each row becomes one chunk: a readable card like 'Vigneshwar B — Manager is X; Project is Y', embedded with all-MiniLM-L6-v2 into a persistent Chroma store.

The core design decision is that retrieval is hybrid, not pure vector search. A router classifies each question into one of four routes — semantic, metadata filter, aggregate, or range.

The reason is that vector search is top-K nearest-neighbour, and K is fixed before you know the answer. Ask 'how many people work on MPLS?' and semantic search with k=4 returns four MPLS employees, and the LLM confidently reports 'four' — when the real answer is twelve. It's not just wrong, it's silently wrong, which is worse. And you can't fix it by raising K: at 97 rows k=100 returns everyone sorted by similarity, so the LLM has to guess where relevance ends — and it doesn't generalize past this dataset anyway.

So those queries take an exact metadata where filter, which returns the complete set, and the count is computed in Python. The LLM never does arithmetic — it only phrases the result."
Q2TRAP QUESTION · FAILURE ANALYSIS MODEL ANSWER

Remove the aggregate route and send "how many people work on MPLS?" to plain semantic search with k=4. What comes back, why is it especially dangerous — and why can't you fix it by raising k to 100?

PART A — THE DANGER IS THE SILENCE
It fails silently and plausibly. If retrieval returned nothing, the user sees an error and knows to distrust it. But semantic search with k=4 cheerfully returns four MPLS employees, and the LLM answers "4 people work on MPLS" — fluent, confident, well-formatted, and wrong. The real number might be 12.

There is no error, no warning, no signal for the user to catch. A confidently wrong number is worse than no answer, because it destroys trust in every other answer the system gives — including the correct ones.

Interview framing: the failure mode that matters in production isn't the one that throws — it's the one that returns something plausible. Say that, and you sound like someone who has operated a system, not just built one.
PART B — WHY k=100 IS NOT A FIX

Two independent reasons, either one fatal:

  1. Rank ≠ match. With 97 employees, k=100 returns all 97, sorted by similarity. Every non-MPLS employee is in there too, just ranked lower. The LLM now has to decide where relevance stops, and nothing in the data marks that boundary. You've moved the counting problem from the retriever into the LLM — the one component you must never trust with a precise count.
  2. It doesn't generalize. k=100 works only because you happen to have 97 rows. At 100,000 employees you'd need k=100000, which is a full table scan with an embedding step bolted on — slower and strictly worse than the filter you should have used. If your fix breaks when the data grows 10×, it isn't a fix.
WHAT YOUR CODE ACTUALLY DOES
src/retrieval.py · _execute_plan()
# AGGREGATE: count. Python owns the number.
results = store.get(where={field: value}) if field else store.get()
docs = _get_result_to_docs(results)
plan["count"] = len(docs)   # ← len(), not the LLM

store.get(where=...) — not similarity_search. Chroma's get() takes no k at all; it returns every matching record. That is the whole point, and it's the sentence to say out loud.

Q3CODE-LEVEL · GUARDRAIL DESIGN MODEL ANSWER

In llm_route() the LLM proposes a field and value, but you don't pass that value into the Chroma where clause — you run it through resolve_value() with a 0.6 fuzzy threshold. What failure does that prevent, and what happens below 0.6?

THE FAILURE IT PREVENTS
The LLM generates a value that is plausible but not present in the store. A metadata filter is an exact string match — where={"manager": "Dhruv"} against a stored value of "Dhruv Sharma" matches zero rows. The user asked a valid question about a real person and gets "no records found."

Typical near-miss shapes the snap repairs:

  • User typo — "dhruv sharmaa" → Dhruv Sharma
  • Partial name — "Dhruv" → Dhruv Sharma
  • Case / whitespace drift — "mpls" → MPLS
  • LLM paraphrase — the model "helpfully" rewrites the value it saw in the prompt

So the guardrail's job is: the LLM may choose the field and intent, but only the store gets to say what values exist. Every filter value is snapped back to a real indexed string before it can touch the query.

WHAT HAPPENS BELOW 0.6 — AND WHY

resolve_value() returns None, llm_route() returns None, and the caller degrades to the rule-based detector, then to semantic search.

A wrong exact filter returns zero rows — a dead end that looks like "this person doesn't exist." Semantic search returns the k nearest cards, which are probably in the right neighbourhood. Degrading to a fuzzy-but-populated result beats failing to an empty-but-precise one.

The threshold is a deliberate two-sided trade:

THRESHOLDCONSEQUENCE
Too low (~0.3)Over-eager snapping — "Anika" matches Anita, and you confidently return the wrong person's data. Worst outcome of all.
0.6Catches typos and partial names; rejects genuinely unrelated strings.
Too high (~0.9)Rejects ordinary typos, so real questions fall through to semantic unnecessarily.
The principle worth naming: never let a generative model's output reach a database query unvalidated. The LLM is a router, not a source of truth — it picks the strategy, the store owns the vocabulary. That same principle is what stops SQL injection in an LLM text-to-SQL system, and it's the transferable version of this answer.
THE DEGRADATION LADDER (say this — it shows systems thinking)
  1. LLM router — schema-aware, handles paraphrase and intent
  2. Rule-based substring scan — works when the gate is down
  3. Semantic search — always returns something usable

Every layer has a strictly weaker dependency than the one above it. The system never returns an error because a component was unavailable — it returns a worse answer instead. That's an availability decision, and interviewers notice when you frame it that way.

Q4CHALLENGE · JUSTIFY THE ARCHITECTURE MODEL ANSWER

"Then why keep the vector store at all? Just use pandas — df[df.Project == 'MPLS'] — or load it into SQLite. Exact answers, no embedding model, no Chroma, no latency."

THE CRACK IN THE CHALLENGE

Pandas and SQL answer exact, structured queries perfectly: df[df["Project"] == "MPLS"] gives every MPLS employee. But try this:

"Who on the team knows automation-ish things?"

There is no automation column. No WHERE automation = True. The answer lives inside embedded text like "works on network automation scripts, familiar with Ansible" — and only cosine similarity over embeddings can surface it. SQL has no operation for "semantically close to this phrase."

WHAT THE EMBEDDING CONTRIBUTES THAT STRING MATCHING NEVER CAN
String matching requires the exact word. Embeddings understand semantic proximity — synonyms, paraphrases, related concepts. "automation-ish" and "Ansible/scripting background" map to nearby vectors in the same space. No SQL predicate can express that relationship.
WHY BOTH ARE NEEDED — THE TWO QUESTION SHAPES
QUESTIONRight toolWhy
"List everyone on MPLS"pandas / SQL / metadata filterExact attribute equality
"Who knows automation-ish things?"Vector searchSemantic proximity, no exact column exists
"How many people under Dhruv?"metadata filter + len()Completeness + counting
"Who has experience similar to Vigneshwar?"Vector searchSimilarity across free-text card

Dropping the vector store means the bottom two rows become unanswerable. That is the concrete gap.

SAY IT LIKE THIS
"Pandas is faster and simpler for exact structured lookups — I use it for those via the metadata filter route. But the moment the question has no column to match on — 'who knows automation-ish things' — SQL has nothing to offer. There's no WHERE for meaning. The embedding model turns the question and every employee card into vectors in the same space, so similarity becomes a distance calculation. Neither tool alone covers both question shapes, which is why the router exists to pick the right one."
Q5YOUR CODE · PHASE 9 SCHEMA INFERENCE MODEL ANSWER

schema.py sorts every column into identity / categorical / numeric / date / freetext. What rule separates categorical from freetext — and what breaks if a freetext column is misclassified as categorical?

THE RULE — EXACT CODE

From src/schema.py — the only two constants that make this decision:

# A column is CATEGORICAL if BOTH are true:
CATEGORICAL_MAX_DISTINCT = 40     # absolute: at most 40 unique values
CATEGORICAL_MAX_RATIO    = 0.5    # relative: distinct/rows below 50%

if len(distinct) <= CATEGORICAL_MAX_DISTINCT and ratio <= CATEGORICAL_MAX_RATIO:
    return ColumnProfile(name, CATEGORICAL, distinct=distinct)

return ColumnProfile(name, FREETEXT)  # high-cardinality → semantic only
The property that makes a column filterable is low cardinality — few enough distinct values that the system can enumerate them, include them in the LLM router prompt, and snap user input to a known value. High-cardinality prose has no enumerable vocabulary, so it goes to semantic search only.
WHAT BREAKS ON MISCLASSIFICATION

The router prompt in src/retrieval.py injects every categorical column's distinct values into the LLM's system message on every query:

shown = vals[:25] + (["..."] if len(vals) > 25 else [])
cat_lines.append(f'  - "{col}" (categorical) values: {shown}')

Three cascading failures if a freetext column (e.g. notes, 97 unique values) is misclassified as categorical:

  1. Prompt bloat. Up to 97 unique prose strings are injected into every LLM router call — burning tokens and inflating latency on every single query.
  2. Broken routing. The LLM tries to snap user input to one of 97 random prose strings. It hallucinates a match, triggers a metadata where filter, and returns zero results for a perfectly valid question.
  3. Semantic path bypassed. Freetext columns are meant to be searched via embeddings. Once misclassified, the system never uses them semantically — the one path that would actually work is silently cut off.
SAY IT LIKE THIS
"A column is categorical when it has few enough distinct values to enumerate — I use an absolute cap of 40 and a ratio cap of 50% of rows. That vocabulary goes into the router's LLM prompt so the model can snap user phrasing to a real stored value. A freetext column fails both thresholds — it has too many distinct values to enumerate, so it's never used as a filter. If you misclassify it as categorical, you inject dozens of prose strings into every prompt, the LLM hallucinates a filter match, and you get zero results — while the semantic path that would have worked sits completely unused."
Q6PRODUCTION · SCALE & BOTTLENECKS MODEL ANSWER

Your system works on 97 employees. You're handed 5 million records and a 200ms p95 latency budget. What breaks first, and what do you change?

WHAT BREAKS FIRST — THE ROUTER PROMPT

The hint is in _known_values() inside src/retrieval.py:

# At query time, reads ALL metadata from Chroma to build the vocab:
metas = store.get()["metadatas"]  # ← 5 million dicts loaded into RAM
for m in metas:
    for k, v in m.items():
        acc.setdefault(k, set()).add(v)
At 97 rows this is invisible. At 5 million rows, every single query loads 5 million metadata dicts into RAM to rebuild the distinct-values vocabulary. That alone exceeds the 200ms budget before a single embedding or LLM call is made.

Then the rebuilt vocabulary — potentially thousands of distinct categorical values — gets injected into the LLM's system prompt. At scale, this overflows the context window entirely.

WHAT YOU CHANGE
PROBLEMFIX
Vocab rebuilt from all rows on every query Pre-compute distinct_values at index time and persist via schema.save() — already wired in, just not used at query time in the fallback path
All distinct values sent to LLM Cap to top-N most frequent per category; the [:25] slice already exists but the underlying load still reads 5M records
Chroma at 5M rows Move to a production ANN backend (Qdrant, Weaviate, pgvector) with HNSW indexing — Chroma is not designed for this scale
Metadata filter is a full scan Maintain a separate SQL table for structured columns; vector store handles semantic only — split the two concerns at the storage layer
SAY IT LIKE THIS
"The first thing to break is the router prompt construction. _known_values() currently calls store.get() with no filter at query time — at 97 rows that's negligible, at 5 million it loads millions of dicts into RAM on every single request before anything else runs. The fix is straightforward in principle: the schema inference already saves the vocabulary to disk at index time via schema.save() — I just need the query path to load from that cache instead of rebuilding it live. Beyond that I'd move the vector store to a proper HNSW-indexed backend like Qdrant, and push exact-filter queries to a SQL table so the vector index only handles the semantic path."
